# Reporting and portal acceptance evidence

`summary_cases.json` supplies actual PostgreSQL reporting tests through `conftest.py`. These fragments are neither production demo data nor complete database insert schemas. The adapter uses the integrated models and commits nested savepoints; the repository test harness rolls back each outer transaction.

## Executed reporting evidence

On 31 October 2026, `.venv/bin/python -m pytest tests/reporting/test_summary.py tests/reporting/test_reports_api.py -q` passed **36 tests** (17 service cases and 19 HTTP cases) against PostgreSQL at port 55431, database `cadentra_experience_test`, using the supplied test-only clock. Ruff check passed for the reporting service, fixture adapter, summary tests and report HTTP tests. The fixture's JSON/Decimal arithmetic was also checked independently before implementation.

These tests exercise actual reporting SQL/service behavior: A/B/combined reconciliation, multiple payments, current-state range independence, active/pause boundaries, internal role enforcement, range/cadence validation, zero-filled daily and clipped monthly series, empty data, customer filtering, and a single read-only summary statement. The HTTP tests create real PostgreSQL users and exercise actual password login, cookie/session authentication, STAFF/ADMIN access, customer 403/anonymous 401, query aliases, default business-month range, customer filtering, monthly cadence, and 422 error envelopes. They do not establish browser behavior, portal lifecycle/printing, concurrency of other modules or T30 performance. No performance claim follows from the test suite's duration.

## Fixture adapter

The adapter uses the integrated model/migration and real PostgreSQL sessions, translates symbolic keys into fresh UUIDs, and supplies required plan, invoice snapshot/line, period and staff actor records. The report HTTP tests additionally create hashed-password users and establish cookie sessions through the real login endpoint; no role dependency is overridden. Give every invoice its own valid billing period and supporting CLOSED subscription so required foreign-key parents do not inflate expected active counts. The listed subscriptions separately exercise reporting eligibility. Monetary totals are final tax-inclusive stored values.

The fixed business clock is 2026-11-02 in Asia/Kolkata. Inject it only through the agreed test clock; do not expose a production request clock override. Roll back or discard the isolated test database between cases. Do not delete shared databases or run against production. The future-start ACTIVE record deliberately verifies defensive reporting filtering even if normal lifecycle activation would not create that state.

The series expectation uses the coordinator-approved DAILY response shape. It specifies all 31 contiguous calendar-day buckets, including zero days; the service tests verify zero-fill behavior. The endpoint has no customer filter in the baseline, so daily-series expectations cover both customers. Summary A uses a staff/admin customer filter; the combined case omits it. Additional response metadata such as `metric_basis` must be verified separately against the documented semantics, rather than rejected merely because this fragment omits it.

## Acceptance scenarios and remaining integration work

- **T28 summary reconciliation:** compare real summary responses with `expectedSummary.A` and `.combined`. Partial balances are exact; the 1000.00 prior-range invoice has two payments, of which only 750.00 falls in range. This detects joined-row double counting and misuse of invoice date for cash. Draft/cancelled invoices do not count; zero-total PAID has no invented payment.
- **T28 dates and current state:** Oct 1 is included; Nov 1 is excluded. The 400.00 invoice due on the clock date is outstanding but not overdue. Change the date range and retain current active/outstanding/overdue values. Verify the business clock rather than the test host timezone determines today. Starting today counts; expiry and effective closure on today do not. Paused/future/expired/draft/closed subscriptions are excluded.
- **T28 series:** compare exact decimal-string values and bucket boundaries to `expectedDailySeries`. Sum buckets and reconcile to the combined range metrics. Check zero-filled empty days, a wholly empty range, month boundaries, and MONTHLY aggregation of this October range (5870.16 invoiced / 3050.00 cash). Verify invalid/reversed ranges, unsupported cadence and the approved 366-day bound through actual API validation.
- **T06 portal isolation:** authenticate two customer sessions. Each list and `/portal/me` returns only its actor's customer data. As A, request B's subscription/invoice detail, invoice print and each pause/resume/close/renew action: expect 404 and no mutation. Supplying B as a `customer_id` must never widen access; the portal contract does not accept that filter. Anonymous requests fail authentication, customers cannot access staff reports, and staff/admin cannot impersonate customers through portal endpoints.
- **T06 safe projections:** populate internal product costs, staff-only notes and private audit fields through real test builders; verify they never appear in customer JSON or printable HTML. Use HTML-like text in customer/product snapshot fields and confirm printing escapes it. Printing must use stored snapshots after catalog/profile edits and must not create invoices or payments.
- **Delegated portal actions:** call the actual subscription service boundary with actor context; validate allowed actions and policy conflicts, accurate scheduled effective dates, and renewal creating a linked DRAFT requiring staff confirmation. Unknown actions and CSRF failures must leave records unchanged. Reuse billing's authorized invoice-query/print service rather than duplicate its rules.
- **T31 browser follow-up:** run the integrated paid-invoice flow, reload and compare reporting/portal values to stored records; inspect desktop/mobile and printable output. This JSON is not browser evidence.
- **T30 performance follow-up:** use a separate expanded disposable dataset (at least 5000 subscriptions and 20000 invoices plus payments). Record environment, commit, row counts, cold/warm state, sample size and actual browser/API p50/p95/max for overview, lists, portal and filtered drilldowns. These small arithmetic cases cannot prove performance.
